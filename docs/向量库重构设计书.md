# 向量库重构设计书

> 状态：**设计定稿，待实施**（2026-09-10 与用户逐轮讨论收敛）
> 目标版本：v3 存储架构（当前为 v2：Milvus 承载全量数据）
> 关联：`ARCHITECTURE.md`、`ADR-004`（切片写耐久）、`ADR-008`（多用户隔离）、`ADR-010`（混合检索）

---

## 1. 背景与问题诊断

当前 Milvus 承担了「向量索引 + 文档存储」双重职责，实测 schema：

| 集合 | 字段数 | 问题 |
|---|---|---|
| `kb_documents` | 14 | 存**文档全文**（content）、summary、状态机字段…… |
| `kb_chunks` | 17 | 存 text、heading、topic、questions、display_title、**pre_context / post_context**（重叠窗口的重复文本）、category、tags + 双向量 |
| `kb_memory` | 10 | 相对合理 |

由此产生的具体问题：

1. **正文三处冗余**：`kb_documents.content`（全文）+ `kb_chunks.text`（切片）+ ES（BM25）——外加 `data/knowledge/`、`data/legacy-backup/` 的历史 JSON 备份
2. **派生数据焊死在向量 schema**：questions / topic 是 LLM 生成的可再生数据，却是一等公民字段，阻碍向「通用智能体」演进（通用场景不需要面试问题锚点，却甩不掉）
3. **换 embedding = 数据搬家**：正文寄生在向量集合里，换模型（nomic→bge-m3）被迫全量迁移正文
4. **分类/标签切片级冗余**：每个切片行都带一份 category/tags，改一次分类要同步几十行（历史 bug 根源）
5. **Milvus 查询与备份被大 payload 拖累**：检索返回 17 字段，其中向量库真正需要的只有 ID 与向量

用户对数据价值的判断（2026-09-10，讨论中拍板）：**双向量（问题向量 + 切片向量）是最核心的检索资产**；标题/主题/标签/分类是轻量元数据；正文不应存在任何数据库里。

## 2. 目标与非目标

**目标**

- G1 每类数据只有一个权威存放地：正文归文件系统，锚点归 SQLite，索引归 Milvus/ES
- G2 Milvus 降级为**纯向量索引**：可整体丢弃、可从持久层一条命令重建
- G3 换 embedding 模型只重建索引层，持久层与锚点层零接触
- G4 去除面试场景特化（questions 从 schema 固有字段降级为普通锚点列），支撑通用智能体方向
- G5 为「文件管理系统」提供数据底座：目录树、切片目录、按锚点取文

**非目标（本轮不做）**

- 前端文件管理界面（数据端点就绪后单独排期）
- 每日 token 预算配额（M5b 遗留，另评估）
- 多实例 / 分布式（ADR-008 既定边界）
- kb_memory 集合重构（本次仅 kb_documents / kb_chunks；kb_memory 现状 0 条，schema 已合理）

## 3. 总体方案：三级存储模型

```
【持久层】本地文件系统 —— 唯一事实源，不可丢，必须备份
  data/files/{owner}/{docId}/
    source.{ext}      用户上传的原件（原样保存）
    content.txt       抽取后的正文（切片与锚点的参照物）

【锚点层】SQLite —— 只存指针与元数据，不存正文
  documents / chunk_catalog（见 §4.2）

【索引层】Milvus + Elasticsearch —— 可丢弃、可随时重建
  Milvus kb_vectors：双向量
  ES：BM25 倒排
```

分层判据：**删掉索引层，业务数据零损失**；删掉锚点层，索引层失去重建依据；删掉持久层，一切归零。备份策略据此调整：文件目录 + `.db` 文件必须备份，Milvus / ES volume 无需备份。

## 4. Schema 设计

### 4.1 文件布局

```
data/files/{owner}/{docId}/
  source.{ext}     原件（pdf/md/docx...，字节原样）
  content.txt      抽取正文（UTF-8；md/html/csv/json 等文本原件可与 source 合一，
                   二进制原件必须单独落盘）
```

- `content.txt` 与切片存在**坐标绑定**：切片锚点 `span(start,end)` 以它的字节/字符偏移为准。因此正文重抽（换解析器）必须触发重切片；`documents.strategy` 记录切片参数保证可复现
- 路径规则 `{owner}/{docId}` 天然按用户分目录，与 ADR-008 的 owner 隔离一致

### 4.2 SQLite（锚点层）

```sql
-- schema_version 沿用 ADR-008 的幂等迁移框架
CREATE TABLE documents (
  doc_id      TEXT PRIMARY KEY,
  owner_id    TEXT NOT NULL,
  title       TEXT NOT NULL,
  ext         TEXT NOT NULL,              -- 原件扩展名
  size        INTEGER NOT NULL,           -- 原件字节数
  path        TEXT NOT NULL,              -- 相对 data/files/ 的路径
  category    TEXT NOT NULL DEFAULT '',   -- 文档级一份，切片不再冗余
  tags        TEXT NOT NULL DEFAULT '[]', -- JSON 数组，文档级
  strategy    TEXT,                       -- 切片策略 JSON（重切片复现用）
  status      TEXT NOT NULL,              -- pending / indexed / error
  error       TEXT,
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);
CREATE INDEX idx_documents_owner ON documents(owner_id, status);
CREATE INDEX idx_documents_cat   ON documents(owner_id, category);

CREATE TABLE chunk_catalog (              -- ★ 切片目录（用户定义的核心表）
  chunk_id    TEXT PRIMARY KEY,
  doc_id      TEXT NOT NULL REFERENCES documents(doc_id) ON DELETE CASCADE,
  owner_id    TEXT NOT NULL,
  idx         INTEGER NOT NULL,           -- 切片编号（文档内序号）
  span_start  INTEGER NOT NULL,           -- ★ 锚点：content.txt 起始偏移（含）
  span_end    INTEGER NOT NULL,           -- ★ 锚点：结束偏移（不含）
  heading     TEXT NOT NULL DEFAULT '',   -- 所属标题（定位辅助，非正文）
  questions   TEXT,                       -- 问题源文本 JSON 数组（锚点：重嵌入依据）
  topic       TEXT,                       -- LLM 派生主题（可再生）
  vec_text    TEXT,                       -- 切片向量在 Milvus 的主键
  vec_quest   TEXT,                       -- 问题向量在 Milvus 的主键（可空）
  vec_model   TEXT,                       -- 生成向量时的 embedding 模型 + 维度
  updated_at  TEXT NOT NULL,
  UNIQUE(doc_id, idx)
);
CREATE INDEX idx_catalog_doc  ON chunk_catalog(doc_id, idx);
CREATE INDEX idx_catalog_owner ON chunk_catalog(owner_id);
```

要点：

- **无 text 列**。正文 = `content.txt[span_start:span_end]`
- `questions` 是**锚点**而非冗余：它是重建问题向量的最小引用信息（无它则换模型后锚点向量永不可再生，只能重跑 LLM）。体积极小（每切片 3 条 × 几十字节）
- `vec_text / vec_quest / vec_model` 合称 vector_ref：目录 ↔ Milvus 的双向定位，且记录生成时的模型/维度，为换模型重建提供依据
- 现行 v2 中 `documents.content`（全文）与 `chunks.pre_context/post_context/display_title` **全部消失**

### 4.3 Milvus（索引层，从 17 字段瘦到 8 个）

```
kb_vectors:
  vec_id      VarChar PK          —— 全局唯一（跨 doc 复用集合）
  owner_id    VarChar             —— 强制过滤（ADR-008）
  doc_id      VarChar             —— 回锚点层
  idx         Int64               —— 回锚点层
  text_vector      FloatVector(dim)
  question_vector  FloatVector(dim)  —— 保留（用户拍板：核心检索资产）
  content_hash     VarChar          —— 增量向量复用（现行能力保留）
```

- 分类/标签过滤不再依赖 Milvus 标量：检索时先由 SQLite 查 `doc_id` 白名单，再 `doc_id in [...]` 下推（数百文档量级毫秒级）。改分类只更新 `documents` 一行
- 双向量仍在一个集合（与现行一致），`unifiedSearch` 的双路召回融合逻辑**不变**，只换数据源
- `kb_memory` 本次不动

### 4.4 Elasticsearch（索引层）

```json
{ "doc_id": "...", "owner_id": "...", "idx": 0, "text": "..." }
```

- ES 持有文本副本是搜索引擎的正常形态（倒排必需），定性为**可重建索引数据**，不计入存储冗余
- `esStore` 现有 `owner_id` 过滤口径保留

## 5. 核心数据流

### 5.1 入库（上传 / doc-processor 确认 / 重切）

```
上传原件 → 落盘 data/files/{owner}/{docId}/source.{ext}
        → 抽取正文 → 写 content.txt
        → SQLite documents(status=pending, strategy 记录)
        → 切片（strategy）→ chunk_catalog 逐条写入（span = 切片时计算的偏移）
        → 双向量化 → insert kb_vectors → 回填 vec_text/vec_quest/vec_model
        → ES 索引（从 content.txt 按 span 取文）
        → documents.status = indexed
```

- 状态机沿用 ADR-004 的写耐久语义：任一步失败停在对应 status，可重放；manifest/锚点已写而索引未写 → 重放只补索引层
- 重切（正文编辑）：覆盖 `content.txt` → 重新切片 → span 全量更新 → 旧向量按 content_hash 复用或重算 → ES 重建该文档

### 5.2 检索（回读）

```
unifiedSearch 双路召回（逻辑不变）
  → Milvus/ES 命中 (doc_id, idx, score)   —— 不再返回任何正文
  → SELECT span, questions FROM chunk_catalog WHERE doc_id=? AND idx=?
  → readFileSync(content.txt).slice(start,end)   —— 按 span 取正文
  → 拼 prompt（引用溯源的 displayTitle 由 documents.title + idx 拼装，不再存储）
```

- 正文读取做一层小 LRU（进程内，命中重复切片时省文件 IO）
- 分类/标签过滤：先查 SQLite 得 doc_id 白名单 → 下推 Milvus/ES

### 5.3 删除（级联，顺序保证可重试）

```
SQLite documents/chunk_catalog（事务内标记 deleting）
  → Milvus deleteBy doc_id  → ES deleteBy query
  → 删除文件目录 → SQLite 物理删除行
```

任一步失败可重试（幂等：Milvus/ES/文件删除均按 ID 幂等）。

### 5.4 对账与重建

- 对账（升级现有孤儿检测）：三方计数比对 —— `chunk_catalog` ↔ Milvus（按 doc_id 分组计数）↔ ES；缺向量/缺 ES 文档 → 自动补索引层
- 全量重建：`reindex` 命令 = 清空/重建 kb_vectors + ES ← 读文件 + chunk_catalog。**不触碰持久层与锚点层**

## 6. 迁移方案（现有 4 篇 / 304 切片，一次性）

```
scripts/migrate-storage-v3.mjs
  --dry-run   默认。读旧集合 → 统计待迁移明细 → 输出报告，不写任何数据
  --apply     执行：
    1. 从旧 kb_documents / kb_chunks 读出全部字段（含双向量）
    2. 按 docId 建 data/files/{owner}/{docId}/：source（从旧 content 生成 md 原件；
       旧数据无原件二进制，v2 上传原件未持久化——见 §8 风险 R2）+ content.txt
    3. 写新 SQLite 表（span 由旧切片 text 在 content 中的 indexOf 顺序计算）
    4. 重建瘦集合 kb_vectors（向量原样搬运，不重算）+ ES
    5. 三方计数校验（documents/chunks/vectors/ES docs 数量一致）
    6. 环境变量开关切到 v3；旧集合改名 kb_documents_v2 / kb_chunks_v2 保留 30 天
```

- 向量**原样搬运不重算**：新旧维度一致（bge-m3 1024），无需重嵌入
- 旧数据无 span → 以切片文本在全文中顺序定位计算；定位失败的切片标记 `status=error` 人工处置（预计极少，重叠窗口切片必然可在全文中找到）
- 迁移脚本独立于服务运行；迁移窗口内知识库只读

## 8. 风险与对策

| # | 风险 | 对策 |
|---|---|---|
| R1 | span 依赖 content.txt 稳定：正文重抽/换解析器会使锚点失效 | strategy 记录 + 「重抽必重切」写入流程；documents.status 的 error 态兜底 |
| R2 | **v2 未持久化上传原件**（二进制只存在于 Milvus content 抽取文本）→ 迁移出的 source 原件只能是抽取文本的 .md，无法还原 pdf/docx 字节 | 接受：迁移生成的 source.md 即为 v3 起点的原件；v3 起上传原件真正落盘。迁移报告中明示每篇的 ext 实际为 md |
| R3 | 文件系统成为单点：磁盘故障即数据丢失 | 备份策略更新：`data/files/` + SQLite 纳入 `scripts/backup-milvus.mjs` 同级备份；Milvus/ES volume 降为可弃 |
| R4 | 切片文本在全文中定位失败（畸形字符/正规化差异） | 定位失败切片标 error 并输出明细；量级预计 0——切片由同一 content 切出 |
| R5 | 双写一致性（SQLite ↔ 索引层） | 沿用 ADR-004 状态机 + §5.4 对账自愈；索引层可整体重建兜底 |

## 10. 文件系统产物与视图合并（2026-09-10 增补）

### 10.1 两层文件产物

入库流水线的文件系统产出固定为两层（外加原件输入）：

```
data/files/{owner}/{docId}/
  source.{ext}      原件（上传输入；文本类原件与 content.md 同源，见 §fileStore 决策 3）
  content.md        【第二层】切片完成后的文档 —— 纯正文（方案 A）
  manifest.json     【第一层】目录文件 —— 本文档的"目录页"
```

- **manifest.json 是投影，权威在锚点层**：入库完成后由 `chunk_catalog` 导出生成；锚点层变化（重切/重嵌入/改元数据）后自动重导；人工编辑 manifest 不生效。目录因此有「机器查库 / 人读文件」两种消费形态，且文件丢失可随时从库重新导出 —— 不构成双写
- **content.md 采用方案 A（纯正文）**：切片边界只存在于目录（span 偏移），正文不含任何切片标记，保持可自由编辑；锚点漂移由「编辑正文必重切」流程约束兜底

### 10.2 文档管理与知识网络合并

原独立的「知识网络」页面（孤立切片语义图，已在仪表盘下线的同源功能）废弃，其 2D/3D 组件并入统一的「知识库」模块。三视图同源：

| 视图 | 数据源 | 说明 |
|---|---|---|
| 文件树 | `data/files/` 实存 + `documents` | 上传 / 下载 / 删除 / 编辑入口 |
| 切片目录 | `chunk_catalog`（= manifest 投影的数据源） | 编号、标题、字数、span、向量引用 |
| 切片阅读 | manifest + content.md | **阅读器**（D10）：按切片分段渲染的沉浸阅读 |
| 知识网络 | 目录切片为**节点**，向量相似度为**边** | 复用现有 2D/3D 组件 |

**节点语义（D9）**：网络图中的文件节点不再指向数据库记录，而是**定位实际文件切片的内容** —— 点击节点 → 锚点（doc_id, idx）→ span → 读 `content.md` 对应片段。图上每一个节点都能落到文件里的真实文本，彻底贯彻「文件为事实源」。

### 10.3 切片阅读器（DocReader，D10）

三栏布局：目录侧栏（切片列表）/ 正文阅读区 / 详情抽屉（heading、topic、questions、向量状态、网络定位入口）。

核心机制 —— **按切片分段渲染**：切片 span 连续无缝覆盖全文，故将 `content.md` 按切片边界切为 N 段，每段独立 Markdown 渲染为 `ChunkBlock`（`data-idx`）。收益：① 偏移在渲染前对齐，无需在渲染后 HTML 中反查位置；② 切片边界天然可视（段间分隔/交替底色）；③ 高亮当前切片 = 高亮单组件，目录点击 `scrollIntoView` 即达。

功能：上一/下一片导航、阅读位置记忆（localStorage per docId）、详情抽屉、知识网络联动定位（当前切片在图中高亮）、编辑入口（走「编辑必重切」流程）。数据流：manifest + content 各拉一次，客户端分段渲染 —— 纯展示层，零新增后端端点；大文档按 span 惰性加载为后续优化。

组件：`DocReaderPage`（路由 `/files/:docId/read`）= `ChunkToc` + `ChunkBlock × N`（内嵌 ReactMarkdown）+ `ChunkDetail`。

|---|---|---|
| D10 | 增设切片阅读器：按切片分段渲染 Markdown，三栏联动 | 目录与正文已齐备，阅读是把「锚点 → 文件」链路呈现给用户的最后一环 |

| # | 决策增补 | 依据 |
|---|---|---|

| D9 | 知识网络节点定位实际文件切片内容（锚点 → 文件） | 强化文件为事实源；图节点与真实文本一一对应 |
