# 切片策略优化计划

## Context

当前 chunker.js 使用固定 800 字窗口 + 120 字 overlap，只认 Markdown 标题作为结构边界。对 Q&A、定义、段落等多种文档格式都会造成语义断裂或数据丢失。需要一个格式无关、语义感知的切片策略。

## 目标

用三层架构实现**格式无关的语义切片**：规则递归做粗切，Embedding 做细切，LLM 做标注。

---

## 完整流程

```
原始文档
  │
  ▼ 第一层：结构化递归切片（规则，0ms）
     Markdown 标题 → 段落（双换行）→ 句子（。！？.!?）
     逐级降级，每一层尊重文档物理结构
     对每个单元检查长度：超限则降级到下一层，达标则保留
  │
  ▼ 第二层：对仍超限的块做语义细切（Embedding）
     按句子分割 → 计算每个句子向量
     相邻句子余弦相似度 → 统计断点（均值 - 标准差）
     在断点处切分
     句子向量复用：chunk 向量 = 句子向量平均值（省掉一次 embed 调用）
  │
  ▼ 上下文扩展（零成本）
     preContext  = 前一个 chunk 最后一两句（约 50~100 字）
     postContext = 后一个 chunk 开头一两句
  │
  ▼ LLM 批量生成描述性标题（一次调用，用本地 Ollama）
     输入：所有 chunk 的摘要
     输出：每个 chunk 一句简短描述性标题（topic）
  │
  ▼ 入库
     { id, docId, text, heading, topic, preContext, postContext, vector, category, tags }
```

## 关键设计

### 1. 结构化递归切片（chunker.js 重写）

```js
function recursiveSplit(text, maxChars = 1000) {
  // 第一层：按 Markdown 标题切
  // 第二层：对超长单元按段落（\n\n）切
  // 第三层：对仍超长的按句子切
  // 每层都检查：单元 ≤ maxChars 则保留，> maxChars 则降级
}
```

递归策略保证物理结构完整性：优先利用文档自带的 Markdown 标题、段落分隔符进行切分，对超长段落逐步降级到句子级别。

### 2. 语义细切（新增 semanticSplit）

```js
function semanticSplit(sentences, sentenceVectors) {
  // 计算相邻句子余弦相似度
  // 断点阈值 = mean - 1 * std（动态统计，不硬编码）
  // 在断点处切分
  // 过短块（< 100 字）向上合并
}
```

只对第一层递归切完后仍然超限的块触发，不是所有块都走这一步。

### 3. Embedding 复用

- 句子向量在语义细切时已经算好
- chunk 向量 = 其句子向量的算术平均
- 不再额外调用 embedTexts（除非无超长块，纯规则切片，此时直接 embed chunk 全文）

### 4. 上下文扩展

- preContext：取前一个 chunk 的最后 1~2 句（约 50~100 字）
- postContext：取后一个 chunk 的开头 1~2 句
- 存入 chunk metadata，检索时拼入上下文送给 LLM
- 零成本，不需要额外 Embedding 或 LLM 调用

### 5. LLM 主题标注

- 用本地 Ollama（免费、快，项目已配置 qwen2.5-coder:14b）
- 批量调用：一次传入所有 chunk 摘要，一次返回所有 topic
- topic 存入 chunk metadata，用于检索结果展示

## 客观评价

### 优点

1. **分工合理**：规则做粗切（快、免费）、Embedding 找语义断点（语义感知）、LLM 做标注（自然语言理解），各司其职
2. **格式无关**：不穷举格式，靠 Embedding 余弦相似度找断点，对 Q&A、段落、定义、表格内容都一视同仁
3. **上下文扩展**：Anthropic 的 Contextual Retrieval 论文验证过，实测检索命中率提升 35%~50%，零成本

### 已知局限

1. **句子向量平均有质量损失**：同主题句子平均偏移小，但"结论句"和"过渡句"权重被拉平，chunk 包含 15~20 句时漂移会显著
2. **断点阈值（mean - std）不稳定**：假设正态分布，但短段落文章 std 很小、话题跳转频繁文章 std 很大，都可能失灵
3. **LLM 标注依赖 Ollama 可用性**：本地服务挂了或模型没拉起来，整个入库链路卡住

## 生产环境加固要点

### 🔴 必须解决

**1. 兜底规则（防止极端 case）**

- 最小块尺寸：≥ 100 字，低于此值向上合并
- 最大块尺寸：≤ 2000 字，超过此值强制硬切（即使没有语义断点）
- 硬切上限：单块不超过 2500 字，防止代码块/表格撑爆上下文窗口
- 断点阈值兜底：阈值不低于 0.5，防止统计失灵

**2. 入库状态管理（防止脏数据）**

```js
// doc 增加状态字段
{
  status: 'pending' | 'indexed' | 'partial' | 'failed',
  indexError: null | 'embed_failed' | 'llm_failed' | ...,
  indexedAt: null | ISO_DATE
}
```

- 文档创建时 status = `pending`
- 切片+向量+标注全部成功 → `indexed`
- 向量成功但 LLM topic 失败 → `partial`（可检索，但 topic 为空）
- 向量失败 → `failed`（需要重试）

**3. LLM 不可用降级方案**

```
Ollama 可用 → LLM 生成 topic
Ollama 不可用 → 降级为 heading（Markdown 标题）
heading 为空 → 降级为 chunk 前 30 字 + "..."
```

任何环节都不应因 LLM 不可用而阻塞入库。

### 🟡 建议优化

**4. 异步补全 chunk 全文向量（先快后准）**

```
用户上传 → 秒回（句子向量平均快速入库）
         → 后台队列补一次 chunk 全文 embed
         → 用全文向量覆盖句子平均向量
```

用户体验：上传即响应，向量精度后台慢慢补。

**5. 句子分割器用 Intl.Segmenter（中英文兼容）**

```js
// 当前正则方案的问题：
// "e.g. React" → 误切成两句
// "U.S.A." → 误切成三句
// 代码注释里的 "." → 不是句子结束

// Intl.Segmenter 原生支持中英文句子边界检测
const segmenter = new Intl.Segmenter('zh-CN', { granularity: 'sentence' })
```

Node.js 16+ 原生支持，零依赖。

**6. LLM 标注幂等性**

- 固定 temperature = 0
- 固定 prompt 模板
- 同一文档上传两次，topic 应一致

### 🟢 后续扩展

**7. 任务队列限流（并发场景）**

多用户同时上传时，Embedding 和 LLM 调用需要排队：
- BullMQ（Redis 驱动，适合分布式）
- p-queue（纯内存，适合单实例）
- 限制 Ollama 并发数（本地模型显存有限）

**8. 异步任务状态查询**

```
POST /api/knowledge/documents → 201（doc 已创建，status = pending）
GET  /api/knowledge/documents/:id/status → { status: 'indexed', progress: '14/14 chunks' }
```

前端轮询或 WebSocket 通知入库完成。
