# ADR-003：采用进程内 TTL/LRU 缓存并以存储写入为一致性边界

## 状态

已接受（2026-08-31）

## 背景

检索、切片预览和查询改写存在重复读取成本，但文档与向量数据必须保持可解释的一致性。项目当前是单 Node 进程，不能假设进程内缓存能在多实例间同步。

## 决策

- 统一使用 `server/lib/cache.js` 的 `TtlLruCache`，必须设置条目上限和/或 TTL；禁止无界 Map。
- `vectorStore` 作为缓存访问门面，Milvus/SQLite/JSON 持久化写入是事实来源。
- 文档新增、编辑、删除及重切片成功后，先完成持久化，再清理相关缓存；失败时不报告成功。
- 查询改写和预览缓存允许短暂陈旧，并以 TTL/LRU 限制内存；跨进程部署必须改为共享缓存或增加失效广播。
- tunables 修改写入 `data/management/tunables.json`，下次启动加载覆盖值；缓存刷新不改变持久化数据。

## 后果

单实例本地运行简单且内存可控，写后失效保证后续读取回到存储层。多实例部署不能仅依赖本地缓存，必须补充共享一致性机制；更换 embedding 模型或维度时需要重建对应 Milvus 集合。
