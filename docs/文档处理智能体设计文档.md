## 1. 背景与定位

当前文档处理是"上传即切片入库"的一步完成流程，用户无法对切片结果做任何干预，也不支持非 Markdown 格式（PDF/DOCX/HTML 网页）的处理。

**文档处理智能体**是一个通用工具型智能体，定位为：
- 用户把原始文档（各种格式）交给它，它能做**预处理 → 切片 → 整理 → 入库**的全链路处理
- 用户可以在对话中随时干预：调整切片策略、合并 chunk、修改内容、改变分类标签
- **不只服务于知识库切片**——任何需要把非结构化文本整理成结构化 chunk 的场景都能用

## 3. 支持的文档格式

| 格式 | 处理方式 | 依赖 |
|------|---------|------|
| `.md/.markdown` | 直接读取文本 | 无 |
| `.txt` | 直接读取文本 + 编码检测 | 现有 `decodeText` |
| `.html/.htm` | HTML → Markdown 转换 | `turndown`（已安装） |
| `.csv/.tsv` | 表格转 Markdown 表格 | 无，字符串处理 |
| `.json` | 结构化内容提取文本 | 无，JSON.stringify |
| `.yaml/.yml` | 直接读取文本 | 无 |
| `.log` | 直接读取文本 | 无 |
| `.pdf` | 文本提取 | 需新增 `pdf-parse`（后续扩展） |
| `.docx` | 文本提取 | 需新增 `mammoth`（后续扩展） |

**当前阶段实现**：md/txt/html/csv/tsv/log/json/yaml/yml（复用现有 `decodeText` + `turndown`）。PDF/DOCX 在文档中预留接口。

## 4. 用户交互流程

### 4.1 整体流程

```
用户对话
  │
  ▼
① 上传文档（或粘贴文本）
  │  → 后端 extractDocumentText() 提取纯文本
  │  → 保存原文到 doc.content，获取 doc id
  │
  ▼
② 智能体分析文档结构
  │  → LLM 分析文档格式特征，推荐切片策略
  │  → 展示：文档概述（字数、段落数、格式类型）
  │
  ▼
③ 用户确认/调整切片策略
  │  → 策略参数：strategy + delimiter + maxChars + hardMaxChars
  │  → 可调多次，每次预览更新
  │
  ▼
④ 执行切片 → 流式预览结果
  │  → 展示每个 chunk 的 heading + chars + 内容预览
  │  → 支持用户说"合并第 2、3 块"、"第 5 块太碎拆分一下"等
  │
  ▼
⑤ 用户确认后入库
  │  → 执行完整 prepareDocChunksAndVectors（切片 + embed + 标注）
  │  → 写入库
  │
  ▼
⑥ 可选：导出整理后的文档
  │  → 用户可以说"把整理好的内容导出为 Markdown"
  │  → 返回合并后的完整文本（用户可下载）
```

### 4.2 典型对话示例

```
用户：[上传一份会议纪要.txt]

Agent：收到，这是一份纯文本会议纪要，共 3,200 字，包含 12 个段落。
       我建议用默认语义切片（按标题→段落→句子），maxChars=800。
       要我预览切片效果吗？

用户：先看看

Agent：[流式输出 5 个 chunk 预览]
       ━━━ 切片预览 ━━━
       第 1 块 · 680 字  |  heading: 会议基本信息
         时间：2026年8月...
       第 2 块 · 720 字  |  heading: 议程一：Q3 目标对齐
         会议首先回顾了...
       ...
       共 5 块，总字数 3,200。确认无误后说"入库"，或告诉我调整策略。

用户：第 2 块和第 3 块合并一下，maxChars 改成 1000

Agent：已重新切片，共 4 块… [新预览]

用户：入库

Agent：✅ 文档《会议纪要.txt》入库成功
       - 切片数：4 块
       - 总字数：3,200
       - 已生成 topic 标注和检索锚点
       可在「知识库」智能体中检索。

用户：把整理后的内容导出为 Markdown

Agent：[返回整理后的完整 Markdown 文本，用户可复制保存]
```

## 5. 后端接口

### 5.1 统一处理入口

```
POST /api/chat（agentName=doc-processor）
```

请求体（JSON）：
```json
{
  "messages": [...],        // AI SDK 标准对话历史
  "agentName": "doc-processor",
  "sessionId": "sess_XX",   // 可选，有则复用
  "action": "upload" | "analyze" | "preview" | "confirm" | "export" | "adjust",
  "text": "...",            // 可选，用户上传的文本（直接从 ChatInput 传入）
  "file": null,             // 可选，multipart 文件（大文件走这个）
  "docId": "doc_1",         // 可选，已有文档的操作
  "strategy": "semantic" | "delimiter",
  "delimiter": "---",       // strategy=delimiter 时
  "maxChars": 800,
  "hardMaxChars": 1600,
  "minChars": 100
}
```

响应：流式 SSE，按 AI SDK data-stream 协议。

### 5.2 action 分支逻辑

```
action=upload（用户上传文件/文本）
  1. extractDocumentText(fileBuffer or text)
     - .md/.txt → decodeText 直接读取
     - .html/.htm → turndown 转 Markdown
     - .csv/.tsv → 表格转 Markdown
     - .json/.yaml → JSON.parse 后提取关键字段
  2. store.createDocument({ title, content: text, category: '', tags: [] })
  3. 返回 doc id + 文档概述（字数/段落数/格式）
  4. 流式输出，引导用户确认策略

action=analyze（分析文档结构）
  1. 读取 doc.content
  2. LLM 分析：判断文档类型、推荐策略
  3. 流式输出分析结果

action=preview（预览切片）
  1. 按参数调用 splitDocumentIntoChunks（不带 embed，不入库）
  2. 流式输出每个 chunk 的 heading + chars + 内容预览（前 150 字）
  3. 附带"建议"：哪块可能需要合并/拆分

action=confirm（确认入库）
  1. 调用 prepareDocChunksAndVectors（完整链路：切片 + embed + 标注）
  2. store.createDocument（如果 doc 不存在）+ store.addChunks
  3. 流式输出入库统计

action=adjust（调整切片）
  1. 根据用户指令（"合并第2、3块"、"拆分第5块"）
  2. 在内存中修改 chunks 数组
  3. 重新 preview，不重新入库
  4. 用户再次 confirm 时以新结果入库

action=export（导出）
  1. 将 chunks 按顺序拼接回完整文本
  2. 流式输出 Markdown 格式文本
  3. 用户可复制保存
```

### 5.3 新增后端模块

**`server/lib/docProcessor.js`（新建）**

```js
/**
 * 文档处理智能体核心逻辑
 *
 * 职责：
 *  1. extractDocumentText(buffer, filename) — 格式感知文本提取
 *  2. analyzeDocStructure(text) — LLM 分析文档结构特征
 *  3. previewChunks(text, strategy, opts) — 仅切片，不入库
 *  4. processAndStore(docId, strategy, opts) — 完整切片+入库
 *  5. applyChunkAdjustment(chunks, adjustment) — 应用用户的 chunk 调整指令
 *  6. exportChunksAsMarkdown(chunks) — 导出为 Markdown
 */
```

**文本提取能力矩阵**：

| 格式 | 提取函数 | 依赖 |
|------|---------|------|
| md/txt/log | `decodeText(buffer)` | 现有 |
| html/htm | `turndown(turndown(document))` | `turndown`（已安装） |
| csv/tsv | `parseCsvToMarkdown(buffer)` | 手写，无依赖 |
| json | `extractJsonText(buffer)` | 手写，无依赖 |
| yaml/yml | `decodeText(buffer)` | 现有 |
| pdf | `pdfParse(buffer)` | 需新增 `pdf-parse` |
| docx | `mammoth.extractText(buffer)` | 需新增 `mammoth` |

## 7. 与知识库上传的关系

```
                    ┌─ 知识库上传入口（现有）
                    │   → 一步完成：上传 + 语义切片 + 入库
                    │
文档 ───────────────┤
                    │   ┌─ 文档处理智能体（新增）
                    └───┤     → 上传/分析 → 预览 → 调整 → 确认 → 入库
                          │     + 导出整理后文本
                          │
                          └─ 用途更广泛：任何需要处理文档的场景
```

**不破坏现有流程**：知识库上传入口保持不变，文档处理智能体作为更灵活的替代。

## 8. LLM Prompt 设计

```
你是一位文档处理专家。你的职责是帮助用户把原始文档整理成适合检索的结构化切片。

处理流程：
1. 用户上传文档后，先分析文档格式和内容结构，给出概述（字数、段落数、格式类型）
2. 根据文档特征推荐合适的切片策略：
   - Markdown 文档 → 默认语义切片（按标题层级切）
   - Q&A 文档 → 建议按问答单元切，maxChars=600
   - 代码文档 → 建议按函数/方法切，maxChars=800
   - 纯文本/OCR 稿 → 建议先做文本清洗，再按段落切
3. 执行切片后展示预览，每个 chunk 显示块号、heading、字数、内容摘要
4. 用户可随时调整：合并块、拆分块、修改策略参数
5. 用户确认后才入库，入库前必须用户明确说"入库"

注意：
- 不要回答文档内容相关的问题（如"这份文档讲了什么"），专注于切片和整理
- 切片预览时不执行 embedding 和 LLM 标注（省成本），只在确认入库时才执行
- 用户可以通过说"导出"把整理后的文本以 Markdown 格式输出
```
