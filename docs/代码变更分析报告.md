## 二、仍存在的小问题

### 1. M5 变体：StreamingMessage debug 日志仍在
**位置**：`src/components/chat/ streamingMessage.jsx:85-102`

```js
// 调试日志：logger.debug 已内置 DEV 门控（生产构建会被剔除）
if (!isUser) {
  log.debug('[StreamingMessage]', { ... })
}
```

当前已改为 `log.debug()`，受 logger 的 DEBUG 门控保护。**但注意**：`logger.js` 的 DEBUG 逻辑是：
```js
const DEBUG = typeof import.meta.env?.DEBUG_LOG !== 'undefined'
  ? import.meta.env.DEBUG_LOG
  : /^(1|true|yes|on)$/i.test(String(localStorage.getItem('DEBUG_LOG') ?? ''))
```
即生产构建时 `import.meta.env` 为 undefined，`localStorage` 无 `DEBUG_LOG` → `DEBUG=false` → 所有 debug 调用静默。**功能正确，但日志仍会在每次渲染时执行对象构造**（轻微性能开销）。

**建议**：改为 `if (DEBUG && !isUser)` 提前短路，避免无效的对象构造。

### 2. L5 仍开放：totalResponseMs 未接入
**位置**：`src/components/chat/SearchProcessPanel.jsx:19-20`

```js
export function SearchProcessPanel({ annotations }) {
  // totalResponseMs prop 已移除 ✅
}
```

经确认，`totalResponseMs` prop 已在上次修复中移除，footer 汇总改用 `totalSearchMs / 1000`。**此问题已修复**。

### 3. 前端 API 客户端未统一使用
**现状**：
- `knowledgeApi.js` 仍使用原始 `fetch`（未走 `src/lib/api.js` 的统一封装）
- `sessionApi.js` 同上
- 只有 `api.js` 有统一错误处理和 requestId 注入

**影响**：知识库和会话相关请求没有 requestId 透传，debug 时难以串联请求。

**建议**：将 `knowledgeApi.js` 和 `sessionApi.js` 改为基于 `api.js` 的 `request()` 函数。

### 4. 启动日志仍用 console.log（可接受）
**位置**：`server/index.js:1171-1238`

启动阶段（端口绑定、健康检查信息、端口占用提示）使用 `console.log/error/warn`。这是**合理且推荐**的——启动日志不属于请求日志，不需要结构化 JSON 格式，也不受 `LOG_LEVEL` 控制。
